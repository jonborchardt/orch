# Fast mode: an explicit single-agent route through the same job workflow

**Decision.** A job has a `mode`, `full` (default) or `fast`, stored on the row (`jobs.mode`,
not null, default `full`) and fixed at creation. Only `orch do <ticket> --fast` creates a fast
job; `orch start`, `orch factory start|dispatch`, the dashboard, and re-land jobs never do, and
nothing classifies tickets automatically. A fast job is created in `build` and goes
build -> pr -> ci -> completed: one agent (`factory-fast-builder`) builds, and spec, simplify,
review, and approve are skipped. The route is a mode-dependent successor of build and a mode-aware
pr and ci completion inside the existing pure `transition`, not a second state machine.

A fast job has no approver, so its approved head is `build.md`'s recorded HEAD.
`approvalEvidence(mode, artifacts)` in `src/core/workflow.ts` is the one place that says which
artifact is the approval (decision.md with `DECISION: APPROVE` for full, build.md for fast); pr
completion, `requireApproved` (and through it push, `pr create`, pr and ci completion),
`verifyOnDisk`, and `integrateBase` all ask it. The delivery rules of
2026-11-14-delivery-gate-binds-the-approval are unchanged: HEAD contains the approved head, only
clean base-integration merges follow it, the tree is clean, verified, and under an authorized
policy. A fast job has no pre-review pass under `ci` authority (`isPreReview` is false for it), so
its delivery always needs build.md's HEAD to hold and its passing CI verdict completes it.

Completing a fast build is refused, with the advice to escalate, when `sensitiveReport` for HEAD
shows a change of kind `policy`, `ci`, `test-config`, or `deps`, a deleted test file, a disabled
or removed test, or policy drift. The check reads the diff without rename detection (a rename is
a delete plus an add) and runs again at every delivery, so neither a rename nor a resume past
build gets around it. A fast job resumes from needs-human only to build, pr, ci, or
completed; running the full workflow is cancel plus `orch ticket reopen` (a new job and branch).

**Exception to decision 39.** "Only approved commits leave the machine" gains a fast-mode
exception: for a fast job the approval is the builder's own `build.md`, bound to a verified HEAD,
not an independent approver's decision. It moves only through the audited `--replace` path when
the builder re-registers it on rework.

**`integrations.decisionHead`.** For a fast job this column records build.md's HEAD. The name is
kept (no schema change beyond `jobs.mode`); the column is evidence only, since `requireApproved`
recomputes the rule from Git.

**Why.** Ticket 0113 asked for less orchestration on small, well-scoped changes without fewer
safety guarantees. Reusing the job row, worktree, lease, events, artifacts, PR, CI reconciliation,
and `mergeJob` keeps every gate that is not a review: verification, the approved-head binding,
CI, the merge rules (including the `workflow-changed` human-merge block). What is given up is the
independent review before an automatic merge in a `mergeRepos` repository; the mitigations are
the per-ticket human opt-in, the sensitive-path refusal, CI, and the unchanged merge rules. A
`MERGE_BLOCKS` code forcing a human merge for fast jobs was considered and not chosen, because the
ticket asks to preserve the existing merge rules; a reviewer of this decision should confirm that
trade-off.

**Benchmark (ticket 0113, not a gate).** Measured by ticket 0125 on job-bd128639 (ticket 0112, a
one-file wording change to a decision file, merged as PR #132), from `orch job usage job-bd128639`:
build 386296 ms (6m 26s), pr 35404 ms (35s), ci 537567 ms (8m 58s, the CI wait through the
merge). Total wall-clock (`wallMs`, job creation to completed) 1028841 ms (17m 9s); without the
ci stage 491274 ms (8m 11s), of which 69574 ms (1m 10s) is time between stages. The run had no
CI repairs or reruns and two verification runs. The 10-minute target, excluding CI, was met, so
no follow-up ticket was filed. One sample on a loaded Windows machine.
